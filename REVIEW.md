# REVIEW.md

## Code Review: Starter `app/main.py`

This document details the defect audit conducted on the starter code in `app/main.py`. Each defect lists its location, root cause, how it manifests under test/scale, and how it was resolved in accordance with `openapi.yaml` and business rules (R1–R10).

The contract requires HTTP 200 only when MongoDB answers, else 503. | Disconnect MongoDB or provide an invalid URI; `GET /health` continues returning 200 OK instead of 503 Service Unavailable. | Added `client.admin.command("ping")` within a try-except block; returns 200 on success and raises `HTTPException(503, "Database unavailable")` on failure. |

## What Was Examined and Decided Was NOT a Defect

1. **`emp_code` as a String instead of ObjectId**:
   - *Consideration*: MongoDB documents typically use `ObjectId` for foreign keys.
   - *Verdict*: Correct as-is. `DATA_MODEL.md` explicitly designates `emp_code` as the natural business identifier across all collections and endpoints; `_id` is strictly internal.

2. **Storing `date` as a String (`"YYYY-MM-DD"`)**:
   - *Consideration*: Why not store dates as BSON datetimes?
   - *Verdict*: Correct as-is. `DATA_MODEL.md` Section 1 notes that calendar dates and shift times are intentionally strings to avoid timezone shift ambiguities. Instants are stored as BSON datetimes; calendar dates represent IST calendar days.

3. **Returning `work_hours: null` for Open Records**:
   - *Consideration*: Should `work_hours` default to `0.0` when an employee is punched in but not yet punched out?
   - *Verdict*: Correct as-is. Rule R4 and `openapi.yaml` explicitly dictate that `work_hours` must remain `null` until punch-out occurs.

4. **Omitting `history` on Creation**:
   - *Consideration*: Should punch-in and punch-out create an entry in `history`?
   - *Verdict*: Correct as-is. `DATA_MODEL.md` Section 4 and `openapi.yaml` state that `history` records manual corrections (regularizations) only; punch-in and punch-out never write to it.
